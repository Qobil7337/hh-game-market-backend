# Ключевые решения

Записка к [README](README.md). Как запустить и воспроизвести сценарии — там;
здесь — почему сделано именно так и что менять под нагрузку.

## 1. Схема данных

| Таблица | Роль | Ограничение, которое держит инвариант |
| --- | --- | --- |
| `orders` | заказ и его статус; **одновременно очередь выдачи** | `status` enum; индекс `(status, updated_at)` для выборки воркером |
| `order_items` | позиция — единица товара со своим статусом и ценой (второе задание) | `status` enum; `UNIQUE (order_id, position)` |
| `payment_events` | каждый вебхук как есть + что мы с ним сделали (`outcome`) | `event_id` — **PK**: повтор события упирается в ключ |
| `deliveries` | факт выдачи: позиция ↔ код | `order_item_id UNIQUE`, `code UNIQUE`, `request_id UNIQUE` |
| `refunds` | факт возврата за позицию | `order_item_id` — **PK**: второй возврат за позицию невозможен |
| `delivery_attempts` | каждый вызов поставщика: исход, деталь, латентность | — (журнал) |
| `supplier_discrepancies` | где ответ или книга поставщика разошлись с нами и что сделано (второе задание) | `UNIQUE (supplier, request_id, kind)` — находка пишется один раз |
| `ledger_entries` | двойная запись денег | `UNIQUE (reason, reference, account)` — нельзя провести факт дважды |
| `products` / `product_stock` | каталог (+ `supplier`, кто держит SKU) и горячий счётчик остатка | `CHECK (available >= 0)` |
| `supplier_keys` | пул ключей **на стороне заглушки** | `request_id UNIQUE` — один `request_id` ⇒ один ключ |
| `supplier_issues` | **книга** заглушки: что она записала под каждым `request_id`; отдаётся по HTTP как выписка | `request_id` — PK; в отличие от пула, один код может стоять под двумя `request_id` — так заглушка врёт |
| `psp_refunds` | возвраты **на стороне заглушки платёжки** | `refund_id` — PK: повтор возврата денег не двигает |

`payment_events.order_id` — текст без внешнего ключа: событие для несуществующего
или кривого `order_id` всё равно должно быть сохранено, а не отброшено.
Сумма заказа фиксируется при создании (снимок цены), вебхук сверяется с ней.

## 2. Exactly-once под гонками

Три независимых уровня, все на стороне Postgres, без блокировок в коде приложения:

1. **`INSERT … ON CONFLICT (event_id) DO NOTHING RETURNING`** — ноль строк в
   ответе означает повтор `event_id`; отвечаем `200 duplicate`, ничего не трогаем.
2. **`SELECT … FOR UPDATE` на строке заказа** внутри той же транзакции. 50
   разных `event_id` на один заказ выстраиваются в очередь на этой блокировке,
   и после ожидания каждая транзакция перечитывает **актуальную** версию
   строки. Поэтому ровно одна видит `created` и применяет платёж, остальные 49
   видят `paid`/`delivered` и записывают себе `ignored_<статус>`.
3. **Compare-and-set на статусе** — `UPDATE orders SET status = 'paid' WHERE id = $1
   AND status = 'created'` (`transitionOrder`). Если совпало 0 строк, переход не
   выполняется. Это защита даже от будущего кода, который забудет взять
   блокировку.

И последний рубеж — `deliveries.order_item_id UNIQUE`: вторую выдачу на позицию
база не примет физически.

Транзакция вебхука короткая (запись события, блокировка, переход) — ответ
платёжке уходит за миллисекунды, HTTP к поставщику в неё не входит.

Тест `races.e2e-spec.ts` поднимает **два экземпляра приложения** (два воркера)
на одной базе и бьёт вебхуками в оба — это ближайшая к «двум репликам за
балансировщиком» модель, доступная внутри одного процесса.

## 3. Очередь — это таблица заказов

Никакого Redis/BullMQ. Воркер забирает работу так:

```sql
SELECT … FROM orders WHERE status = 'paid'
ORDER BY updated_at FOR UPDATE SKIP LOCKED LIMIT 1;
UPDATE orders SET status = 'delivering' WHERE id = $1 AND status = 'paid';
```

`SKIP LOCKED` позволяет любому числу «дорожек» (`DELIVERY_CONCURRENCY`) и
экземпляров приложения разбирать очередь без координации и без двойного
захвата. Постановка в очередь — это тот же `UPDATE`, что подтверждает оплату, в
той же транзакции: нет отдельного outbox и нет окна «оплата записана, задача
потеряна». После коммита вебхук будит воркер (`wake()`), периодический опрос —
только страховка.

Почему не брокер: одна база вместо двух систем с разной семантикой доставки;
транзакционная постановка «бесплатно»; объём — сотни заказов в секунду на одном
Postgres без усилий. Когда очередь перестанет помещаться в один инстанс, эта
же таблица становится outbox для Kafka/RabbitMQ — контракт воркера не меняется.

## 4. Поставщики: таймаут ≠ отказ

`request_id = "<order_item_id>:<supplier>"` — стабильный на позицию и
поставщика, а не на попытку. Повтор после таймаута предъявляет тот же id, и поставщик обязан
вернуть тот же код. Заглушка так и делает: `pg_advisory_xact_lock(hashtext(request_id))`
сериализует гонку «оригинал против повтора», затем поиск по `request_id`, и
только если пусто — резерв свободного ключа через `FOR UPDATE SKIP LOCKED`.
Зависание в заглушке происходит **после коммита** ключа и вне транзакции — это
и есть ловушка: код уже выдан, ответ не дошёл, повтор не должен блокироваться.

Классификация ответа в `DeliveryService`:

| Ответ | Смысл | Действие |
| --- | --- | --- |
| `200 ok` | заявлен код | сверить с книгой и выдать (см. §8) |
| `out_of_stock` | **определённо** ничего не выдано | следующий поставщик, без повторов |
| `ECONNREFUSED`, `ENOTFOUND` | запрос не ушёл — определённо ничего не выдано | бэкофф 500·2ⁿ мс, до 3 попыток, затем следующий поставщик |
| `5xx`, **таймаут** | **неизвестно** — код мог быть записан | повтор **тому же** поставщику с **тем же** `request_id`; после попыток — чтение его книги: код есть → выдать его, пусто → следующий поставщик, книга недоступна → `delivery_failed`, **на B не уходим** |

Правило, из которого всё следует: **поставщик, не давший определённого ответа,
«держит» позицию, пока его книга не скажет, выдал он код или нет**. Переключение
на B раньше — единственный способ выдать клиенту два кода. `out_of_stock` на
повторе тоже закрывает вопрос: поставщик ищет по `request_id` раньше, чем
резервирует, значит зависший вызов ничего не выдал. В первом этапе 5xx считался
определённым отказом и книги не было — правило «держит» работало только по
таймауту; во втором задании (§8) 5xx уравнен с таймаутом, а книга стала
арбитром, и «сознательное ограничение» первого этапа — ждать молчащего
поставщика неограниченно — осталось только для случая, когда недоступна и его
книга.

Это правило переживает рестарты и ручные повторы: перед выдачей
`supplierChain()` перечитывает `delivery_attempts` и ставит первым поставщика,
чьё последнее слово — таймаут или ошибка. Без этого сценарий «A отказал
определённо → B завис → парковка → оба починились → повтор» начинал бы снова с A
и выдавал второй ключ, пока B хранит первый. Хаос-тест (`suppliers.e2e-spec.ts`)
со случайными 5xx и зависаниями на обоих поставщиках проверяет именно «≤ 1 ключа
на заказ» до и после починки.

## 5. Восстановление, сверка, журнал

**Восстановление** (`RecoveryService`, раз в `RECOVERY_INTERVAL_MS`): `delivering`
старше `DELIVERY_STALE_AFTER_MS` (воркер умер посреди выдачи) и запаркованные
старше `RECOVERY_RETRY_AFTER_MS` возвращаются в `paid` одним условным `UPDATE … RETURNING`.
Безопасно, потому что повторная выдача идемпотентна: те же `request_id`,
история попыток учитывается, финализация — compare-and-set.

**Сверка** (`GET /admin/reconciliation`) — набор SQL по таблицам, которые
обязаны сходиться: «оплачен, но не выдан» (транзиентно, старые — застрявшие);
«выдан, но не оплачен» (должно быть пусто); события, которые не удалось
применить (`order_not_found`, `amount_mismatch`); `paid` после `payment_failed`
(кандидаты на возврат); ключи у поставщика без выдачи (след таймаута до
восстановления); ключ у поставщика при выдаче другим кодом (должно быть пусто).

**Журнал** — двойная запись со знаком: активы `+`, обязательства и выручка `−`,
поэтому **сумма всей таблицы всегда 0**. Оплата заказа: `cash +A`,
`customer_liability −A`; выдача позиции: `customer_liability +a`, `revenue −a`;
возврат позиции: `customer_liability +a`, `cash −a`. Проводки пишутся в **той
же транзакции**, что и переход статуса, а `UNIQUE (reason, reference, account)`
не даёт провести факт дважды. Сверка сопоставляет балансы с позициями: `cash`
= оплачено − возвращено, `customer_liability` = ещё открыто, `revenue` =
выдано, `refunded` = возвращено. Каждый e2e-тест заканчивается этой проверкой
прямо в базе.

**Логи** — штатный `ConsoleLogger({ json: true })`, по объекту на событие:
`payment.webhook`, `delivery.attempt` (с `request_id`, исходом и латентностью),
`delivery.completed`, `delivery.parked`, `recovery.sweep`. Кода ключа в логах нет.

## 6. Каталог под нагрузкой

Остаток вынесен в узкую таблицу `product_stock (sku PK, available, updated_at)`
и списывается в транзакции выдачи: широкая, почти неизменяемая строка товара не
переписывается на каждой продаже, а витрина никогда не считает ключи `COUNT(*)`.

Горячий запрос — витрина с фильтром по типу и keyset-пагинацией по `sku`:

```sql
SELECT p.sku, p.name, p.type, p.price, p.currency, p.image, s.available
FROM products p
JOIN LATERAL (SELECT available FROM product_stock s
              WHERE s.sku = p.sku AND s.available > 0 LIMIT 1) s ON true
WHERE p.active AND p.type = $1 AND p.sku > $2   -- $2 — последний sku предыдущей страницы
ORDER BY p.sku LIMIT 51;
```

Индекс: `products (type, sku) WHERE active` — частичный, покрывает и фильтр, и
порядок, так что сортировки нет. План на 100 012 SKU (`GET /admin/explain`):

```
Limit  (actual time=0.160..0.271 rows=51)            Buffers: shared hit=211
  -> Nested Loop
       -> Index Scan using products_type_sku_active_idx on products p  (rows=51, Buffers: 7)
            Index Cond: (type = 'key')
       -> Limit (loops=51)
            -> Index Scan using <PK product_stock> on product_stock s   (Buffers: 204)
                 Index Cond: (sku = p.sku)   Filter: (available > 0)
Execution Time: 0.301 ms
```

(Имена PK в реальном выводе сгенерированы TypeORM: `PK_d16a…`.)

Стоимость — ~4 страницы на строку результата и не зависит ни от размера
каталога, ни от глубины пагинации (страница с курсором на 50 000-й позиции —
215 буферов, 0,23 мс). `OFFSET` дал бы линейный рост; keyset — нет.

Почему `LATERAL … LIMIT 1`, а не обычный `JOIN`: с обычным соединением планировщик
выбирал **Merge Join** и на первой странице проходил `product_stock` с самого
начала, пока не догонял сторону товаров (24 675 строк, 1 021 буфер, 8,5 мс) —
O(позиции в каталоге) вместо O(страницы). Коррелированный подзапрос с `LIMIT 1`
(на PK это no-op) не даёт втянуть его в соединение и фиксирует вложенный цикл
с точечными обращениями по PK.

Следующий шаг, если доля товаров без остатка станет большой: флаг
`products.in_stock`, который меняется только при переходе `available` через 0
(редко), и индекс `(type, sku) WHERE active AND in_stock` — тогда фильтр по
остатку уходит в индекс товаров, а `product_stock` читается только ради числа.

## 7. Второе задание, задача 1: несколько товаров, частичная выдача, возвраты

**Единица выдачи — позиция, а не заказ.** `order_items` — по строке на единицу
товара со своей ценой, статусом, `request_id`, выдачей и, если дошло до
этого, возвратом. Заказ хранит только сумму (для сверки с вебхуком) и статус,
который **выводится** из позиций в конце прохода: все выданы — `delivered`,
никакая — `refunded`, иначе `partially_delivered`; есть открытые —
`delivery_failed` (восстановимый). Очередь, вебхук, `SKIP LOCKED` и
compare-and-set из первого этапа не изменились — они работают на заказе; всё
новое — внутри прохода `DeliveryService.deliver()`.

**Кто выдаёт.** У SKU есть «свой» поставщик (`products.supplier`); цепочка для
позиции — он, затем остальные как fallback. Правило «таймаут держит» из §4
осталось на уровне позиции: поставщик с открытым таймаутом идёт первым.

**Когда возвращать, а когда ждать.** Возврат — только по **определённому**
«нет» от всех поставщиков (`out_of_stock` или 5xx до выдачи). Позиция, по
которой поставщик замолчал после возможной выдачи, не возвращается: иначе
покупатель может получить и деньги, и код, а мы — счёт от поставщика. Она
остаётся `pending`, заказ паркуется, recovery дожимает тем же `request_id`. Это
осознанный выбор «подождать поставщика» вместо «вернуть деньги сразу», и он
же объясняет, почему `out_of_stock`-парковка первого этапа заменена возвратом:
раз ответ определённый, честнее вернуть деньги, чем держать заказ.

**Возврат в три шага, каждый повторяемый.**

1. Решение: `pending → refunding` (compare-and-set, с причиной). После этого
   поставщиков за эту позицию больше не спрашивают, даже после рестарта.
2. Вызов платёжки с `refund_id = order_item_id`. Заглушка идемпотентна по
   `refund_id` (PK в `psp_refunds`), как поставщик — по `request_id`.
   Отказ/таймаут → позиция остаётся `refunding`, заказ в `delivery_failed`,
   следующий проход повторяет вызов.
3. Проводка: `INSERT refunds ON CONFLICT DO NOTHING` + `refunding → refunded`
   + проводки журнала — в одной транзакции.

Ни один шаг нельзя выполнить дважды с последствиями: второй раз упрётся в PK,
в compare-and-set или в `UNIQUE` журнала.

**Повтор прохода** (`/deliver`, recovery, воркер после аварии) читает позиции и
пропускает `delivered`/`refunded`; `pending` идёт по цепочке (с учётом
`delivery_attempts`), `refunding` — сразу на шаг 2. Тест «воркер умер после
первой позиции» в `multi-item.e2e-spec.ts` воспроизводит ровно то состояние,
которое остаётся после падения: `delivering`, одна позиция выдана, у B лежит
ключ второй.

**Инвариант денег** — `оплачено = выдано + возвращено + открыто`, у финального
заказа `открыто = 0`. Он проверяется тремя способами: `money` в `GET /orders/:id`
(по позициям), `moneyMismatches` в сверке (позиции против проводок журнала по
каждому заказу) и `expectConsistent` в конце каждого теста (плюс: число
возвратов у нас = число возвратов у платёжки = число `refunded`-позиций).

## 8. Второе задание, задача 2: поставщик, которому нельзя доверять

**Модель угрозы.** Заглушка теперь умеет: записать под наш `request_id` код,
который уже выдала кому-то (`duplicateRate`); записать один код, а в ответе
прислать другой — чужой или выдуманный (`foreignRate`); записать код и
ответить 5xx (`errorAfterIssueRate`). Общее у всех трёх: **ответ расходится с
книгой**. Поэтому ответ — заявление, а фактов два, и оба у нас под контролем:

1. **Книга поставщика** — `GET /issued?request_id=…`. Это не «доверие
   поставщику», а сверка с тем, за что он выставит счёт: если он записал K1, а
   прислал K2, платить мы будем за K1, и покупатель должен получить K1. Книга
   читается по HTTP с тем же таймаутом, что и `issue`; заглушка «висит» и на
   ней тоже, поэтому недоступный поставщик остаётся недоступным целиком.
2. **`deliveries.code UNIQUE`** — код физически не может быть выдан дважды,
   что бы ни прислали.

**Что происходит с каждым ответом** (`DeliveryService.accept()`):

| Ответ / книга | Расхождение | Действие |
| --- | --- | --- |
| `ok K`, книга `K` | — | выдать |
| `ok K2`, книга `K1` | `code_mismatch` | выдать **K1**, K2 никуда не уходит |
| `ok K`, книги нет | `unbooked_code` | отклонить, новый раунд |
| книга подтвердила, но `INSERT deliveries` упёрся в `code UNIQUE` | `duplicate_code` | отклонить, новый раунд |
| 5xx/таймаут ×3, книга `K` | `error_but_issued` (для 5xx) | выдать K, **второго запроса нет** |
| 5xx ×3, книги нет | — (`none_issued`) | следующий поставщик |
| таймаут ×3, книги нет — **в этом же проходе** | — | `delivery_failed`: запрос мог ещё выполняться у поставщика, пустая книга «прямо сейчас» ничего не доказывает |
| таймаут ×3, книги нет — **на следующем проходе** (после паузы recovery или `/deliver`) | — (`none_issued`) | следующий поставщик |
| 5xx/таймаут ×3, книга недоступна | — | `delivery_failed`, ждать |

Строка про таймаут — не теория: хаос-тест первого этапа поймал именно её. Под
нагрузкой заглушка коммитила ключ на несколько миллисекунд позже, чем клиент
сдался, книга в тот момент была пуста, и позиция ушла к B — два ключа на заказ.
5xx такой дыры не имеет: ответ означает, что поставщик с запросом закончил.

**Раунды.** Отклонённый код нельзя «перепросить» тем же `request_id` — честная
идемпотентность вернёт тот же плохой код. Поэтому следующий раунд идёт под
`<item>:<supplier>:2`, `:3` (`SUPPLIER_MAX_ROUNDS`), после чего поставщик
считается отказавшим и очередь переходит к запасному. Номер раунда не хранится
отдельно: он равен числу отклонений (`duplicate_code` + `unbooked_code`) по этой
позиции и поставщику, так что рестарт продолжает с правильного `request_id`.
Отклонённые записи остаются в книге поставщика под нашими `request_id` — это
его проблема, и у нас на каждую есть строка расхождения с `resolution`.

**Аудит книги** (`SupplierAuditService`, раз в `SUPPLIER_AUDIT_INTERVAL_MS`,
и `POST /admin/supplier-audit`) — вторая линия: читает всю выписку и
сравнивает с `deliveries`/`delivery_attempts`. Находит то, чего момент выдачи
видеть не мог: `request_id`, который мы не посылали (`unknown_request`); код,
записанный под `request_id` позиции, закрытой без него (`unused_issue`);
код в книге, изменившийся после выдачи (`code_mismatch`). Запись в
`supplier_discrepancies` уникальна по `(supplier, request_id, kind)` и уже
объяснённые `request_id` пропускаются — второй прогон ничего не добавляет.
«Разбор без ручного вмешательства» здесь означает: каждое расхождение имеет
записанное действие (выдан код из книги / код не использован / спор), покупатель
никогда не ждёт этого разбора, а сверка показывает список для претензии
поставщику. Единственное, что делает `healthy=false`, — код в книге, не
совпадающий с уже выданным: покупатель код не теряет, но счёт от поставщика
будет спорным.

**Цена.** Одна дополнительная HTTP-сверка на выдачу и одна на «неопределённый»
отказ. Для поставщика, которому нельзя доверять, это дешевле любого
альтернативного контроля; для честного — можно отключить сверку по
поставщику (не сделано: задание про недоверие).

**Инвариант в тестах** (`expectConsistent`): каждый выданный код есть в книге
своего поставщика под тем `request_id`, под которым выдан; число записей книги
без выдачи равно числу объяснённых расхождений (`duplicate_code`,
`unused_issue`, `unknown_request`); кодов в `deliveries` столько же, сколько
уникальных. Хаос-тест `untrusted.e2e-spec.ts` включает все три вида лжи
одновременно с 5xx и зависаниями на обоих поставщиках.

## 9. Что сознательно упрощено

- Нет аутентификации на `/admin/*` и заглушках — задание не просит, а
  воспроизводимость через `curl` важнее.
- Одна валюта; суммы в целых рублях, как в каталоге. Возвраты — только за
  невыданные позиции; `paid` после `payment_failed` по-прежнему только попадает
  в сверку.
- Заглушка платёжки умеет только принимать возвраты и отвечать 5xx; входящие
  платежи, как и раньше, эмулирует `scripts/pay.mjs` вебхуками.
- Книга поставщика (`GET /issued`) — расширение контракта на стороне заглушки:
  у реального поставщика это выписка/статус заказа по `request_id`. Без неё
  «ошибка, но код выдан» неразрешима в принципе — любой ответ можно
  подделать.
- Аудит читает всю выписку целиком (до 1000 записей); в реальности —
  `?since=` по времени последней сверки.
- Схема через `synchronize`, миграций нет.
- Поставщики-заглушки в том же процессе и той же базе — но вызываются по HTTP с
  настоящими таймаутами; их состояние (`supplier_keys`) — «чужие» данные,
  приложение к ним не обращается.
- Тесты очищают сконфигурированную базу.

## 10. Как масштабировать под нагрузку

- **Горизонтально — уже сейчас.** Экземпляры делят только Postgres; воркеры
  разбирают очередь через `SKIP LOCKED`, восстановление идемпотентно, тесты это
  моделируют двумя приложениями на одной базе.
- **Путь вебхука** — две-три короткие команды под блокировкой одной строки;
  конкуренция возможна только между событиями *одного* заказа, что и требуется.
  Пул соединений — единственный ресурс, за которым надо следить: ожидающие
  блокировку транзакции держат соединение, поэтому HTTP к поставщику вынесен
  из транзакции.
- **Очередь.** Частичный индекс `orders (status, updated_at) WHERE status IN
  ('paid','delivering',…)` вместо полного, чтобы горячая часть не росла с историей;
  архивирование финальных заказов старше N дней в отдельную таблицу/партицию.
  При росте за пределы одного Postgres — та же таблица как outbox в брокер.
- **Поставщики.** Per-supplier circuit breaker (после K определённых отказов
  подряд идти сразу к B), лимит одновременных запросов на поставщика, джиттер в
  бэкоффе. Политика по таймауту не меняется: она про корректность, а не про
  скорость.
- **Витрина.** Запрос уже O(страницы); дальше — read-replica для чтения
  каталога и кэш страниц с инвалидацией по `product_stock.updated_at`;
  счётчик остатка обновляется в транзакции выдачи, поэтому расхождений с базой
  у кэша нет — только запаздывание.
- **Наблюдаемость.** Логи уже структурированные; следующий шаг — метрики по
  `delivery_attempts` (латентность и доля исходов по поставщику) и алерт на
  `paidNotDelivered` старше порога из сверки.
