# Ключевые решения

Записка к [README](README.md). Как запустить и воспроизвести сценарии — там;
здесь — почему сделано именно так и что менять под нагрузку.

## 1. Схема данных

| Таблица | Роль | Ограничение, которое держит инвариант |
| --- | --- | --- |
| `orders` | заказ и его статус; **одновременно очередь выдачи** | `status` enum; индекс `(status, updated_at)` для выборки воркером |
| `payment_events` | каждый вебхук как есть + что мы с ним сделали (`outcome`) | `event_id` — **PK**: повтор события упирается в ключ |
| `deliveries` | факт выдачи: заказ ↔ код | `order_id UNIQUE`, `code UNIQUE`, `request_id UNIQUE` |
| `delivery_attempts` | каждый вызов поставщика: исход, деталь, латентность | — (журнал) |
| `ledger_entries` | двойная запись денег | `UNIQUE (reason, reference, account)` — нельзя провести факт дважды |
| `products` / `product_stock` | каталог и горячий счётчик остатка | `CHECK (available >= 0)` |
| `supplier_keys` | пул ключей **на стороне заглушки** | `request_id UNIQUE` — один `request_id` ⇒ один ключ |

`payment_events.order_id` — текст без внешнего ключа: событие для несуществующего
или кривого `order_id` всё равно должно быть сохранено, а не отброшено.
Сумма заказа фиксируется при создании (снимок цены), вебхук сверяется с ней.

## 2. Exactly-once под гонками

Три независимых уровня, все на стороне Postgres, без блокировок в коде приложения:

1. **`INSERT … ON CONFLICT (event_id) DO NOTHING RETURNING`** — ноль строк в
   ответе означает повтор `event_id`; отвечаем `200 duplicate`, ничего не трогаем.
2. **`SELECT … FOR UPDATE` на строке заказа** внутри той же транзакции. 50
   разных `event_id` на один заказ выстраиваются в очередь на этой блокировке,
   и после ожидания каждая транзакция перечитывает **актуальную** версию
   строки. Поэтому ровно одна видит `created` и применяет платёж, остальные 49
   видят `paid`/`delivered` и записывают себе `ignored_<статус>`.
3. **Compare-and-set на статусе** — `UPDATE orders SET status = 'paid' WHERE id = $1
   AND status = 'created'` (`transitionOrder`). Если совпало 0 строк, переход не
   выполняется. Это защита даже от будущего кода, который забудет взять
   блокировку.

И последний рубеж — `deliveries.order_id UNIQUE`: вторую выдачу на заказ база не
примет физически.

Транзакция вебхука короткая (запись события, блокировка, переход) — ответ
платёжке уходит за миллисекунды, HTTP к поставщику в неё не входит.

Тест `races.e2e-spec.ts` поднимает **два экземпляра приложения** (два воркера)
на одной базе и бьёт вебхуками в оба — это ближайшая к «двум репликам за
балансировщиком» модель, доступная внутри одного процесса.

## 3. Очередь — это таблица заказов

Никакого Redis/BullMQ. Воркер забирает работу так:

```sql
SELECT … FROM orders WHERE status = 'paid'
ORDER BY updated_at FOR UPDATE SKIP LOCKED LIMIT 1;
UPDATE orders SET status = 'delivering' WHERE id = $1 AND status = 'paid';
```

`SKIP LOCKED` позволяет любому числу «дорожек» (`DELIVERY_CONCURRENCY`) и
экземпляров приложения разбирать очередь без координации и без двойного
захвата. Постановка в очередь — это тот же `UPDATE`, что подтверждает оплату, в
той же транзакции: нет отдельного outbox и нет окна «оплата записана, задача
потеряна». После коммита вебхук будит воркер (`wake()`), периодический опрос —
только страховка.

Почему не брокер: одна база вместо двух систем с разной семантикой доставки;
транзакционная постановка «бесплатно»; объём — сотни заказов в секунду на одном
Postgres без усилий. Когда очередь перестанет помещаться в один инстанс, эта
же таблица становится outbox для Kafka/RabbitMQ — контракт воркера не меняется.

## 4. Поставщики: таймаут ≠ отказ

`request_id = "<order_id>:<supplier>"` — стабильный на заказ и поставщика, а не
на попытку. Повтор после таймаута предъявляет тот же id, и поставщик обязан
вернуть тот же код. Заглушка так и делает: `pg_advisory_xact_lock(hashtext(request_id))`
сериализует гонку «оригинал против повтора», затем поиск по `request_id`, и
только если пусто — резерв свободного ключа через `FOR UPDATE SKIP LOCKED`.
Зависание в заглушке происходит **после коммита** ключа и вне транзакции — это
и есть ловушка: код уже выдан, ответ не дошёл, повтор не должен блокироваться.

Классификация ответа в `DeliveryService`:

| Ответ | Смысл | Действие |
| --- | --- | --- |
| `200 ok` | выдано | завершить |
| `out_of_stock` | **определённо** ничего не выдано | следующий поставщик, без повторов |
| `5xx`, `ECONNREFUSED` | определённо ничего не выдано | бэкофф 500·2ⁿ мс, до 3 попыток, затем следующий поставщик |
| **таймаут** | **неизвестно** — код мог быть выдан | повтор **тому же** поставщику с **тем же** `request_id`; если ответа так и нет — `delivery_failed`, **на B не уходим** |

Правило, из которого всё следует: **поставщик, ответивший таймаутом, «держит»
заказ, пока не ответит `ok` или `out_of_stock`**. Переключение на B в этот момент
— единственный способ выдать клиенту два кода. `out_of_stock` на повторе тоже
закрывает вопрос: поставщик ищет по `request_id` раньше, чем резервирует, значит
зависший вызов ничего не выдал.

Это правило переживает рестарты и ручные повторы: перед выдачей
`supplierChain()` перечитывает `delivery_attempts` и ставит первым поставщика,
чьё последнее слово — таймаут. Без этого сценарий «A отказал определённо → B
завис → парковка → оба починились → повтор» начинал бы снова с A и выдавал
второй ключ, пока B хранит первый. Хаос-тест (`suppliers.e2e-spec.ts`) со
случайными 5xx и зависаниями на обоих поставщиках проверяет именно «≤ 1 ключа
на заказ» до и после починки.

Сознательное ограничение: заказ, запаркованный на «молчащем» поставщике, ждёт
его ответа; принудительный fallback — это действие оператора с записью в сверку,
а не автоматика.

## 5. Восстановление, сверка, журнал

**Восстановление** (`RecoveryService`, раз в `RECOVERY_INTERVAL_MS`): `delivering`
старше `DELIVERY_STALE_AFTER_MS` (воркер умер посреди выдачи) и запаркованные
старше `RECOVERY_RETRY_AFTER_MS` возвращаются в `paid` одним условным `UPDATE … RETURNING`.
Безопасно, потому что повторная выдача идемпотентна: те же `request_id`,
история попыток учитывается, финализация — compare-and-set.

**Сверка** (`GET /admin/reconciliation`) — набор SQL по таблицам, которые
обязаны сходиться: «оплачен, но не выдан» (транзиентно, старые — застрявшие);
«выдан, но не оплачен» (должно быть пусто); события, которые не удалось
применить (`order_not_found`, `amount_mismatch`); `paid` после `payment_failed`
(кандидаты на возврат); ключи у поставщика без выдачи (след таймаута до
восстановления); ключ у поставщика при выдаче другим кодом (должно быть пусто).

**Журнал** — двойная запись со знаком: активы `+`, обязательства и выручка `−`,
поэтому **сумма всей таблицы всегда 0**. Оплата: `cash +A`,
`customer_liability −A`; выдача: `customer_liability +A`, `revenue −A`. Проводки
пишутся в **той же транзакции**, что и переход статуса, а `UNIQUE (reason,
reference, account)` не даёт провести факт дважды. Сверка сопоставляет балансы
с таблицей заказов: `cash` = сумма оплаченных, `customer_liability` = сумма
оплаченных-но-не-выданных, `revenue` = сумма выданных. Каждый e2e-тест
заканчивается этой проверкой прямо в базе.

**Логи** — штатный `ConsoleLogger({ json: true })`, по объекту на событие:
`payment.webhook`, `delivery.attempt` (с `request_id`, исходом и латентностью),
`delivery.completed`, `delivery.parked`, `recovery.sweep`. Кода ключа в логах нет.

## 6. Каталог под нагрузкой

Остаток вынесен в узкую таблицу `product_stock (sku PK, available, updated_at)`
и списывается в транзакции выдачи: широкая, почти неизменяемая строка товара не
переписывается на каждой продаже, а витрина никогда не считает ключи `COUNT(*)`.

Горячий запрос — витрина с фильтром по типу и keyset-пагинацией по `sku`:

```sql
SELECT p.sku, p.name, p.type, p.price, p.currency, p.image, s.available
FROM products p
JOIN LATERAL (SELECT available FROM product_stock s
              WHERE s.sku = p.sku AND s.available > 0 LIMIT 1) s ON true
WHERE p.active AND p.type = $1 AND p.sku > $2   -- $2 — последний sku предыдущей страницы
ORDER BY p.sku LIMIT 51;
```

Индекс: `products (type, sku) WHERE active` — частичный, покрывает и фильтр, и
порядок, так что сортировки нет. План на 100 012 SKU (`GET /admin/explain`):

```
Limit  (actual time=0.160..0.271 rows=51)            Buffers: shared hit=211
  -> Nested Loop
       -> Index Scan using products_type_sku_active_idx on products p  (rows=51, Buffers: 7)
            Index Cond: (type = 'key')
       -> Limit (loops=51)
            -> Index Scan using <PK product_stock> on product_stock s   (Buffers: 204)
                 Index Cond: (sku = p.sku)   Filter: (available > 0)
Execution Time: 0.301 ms
```

(Имена PK в реальном выводе сгенерированы TypeORM: `PK_d16a…`.)

Стоимость — ~4 страницы на строку результата и не зависит ни от размера
каталога, ни от глубины пагинации (страница с курсором на 50 000-й позиции —
215 буферов, 0,23 мс). `OFFSET` дал бы линейный рост; keyset — нет.

Почему `LATERAL … LIMIT 1`, а не обычный `JOIN`: с обычным соединением планировщик
выбирал **Merge Join** и на первой странице проходил `product_stock` с самого
начала, пока не догонял сторону товаров (24 675 строк, 1 021 буфер, 8,5 мс) —
O(позиции в каталоге) вместо O(страницы). Коррелированный подзапрос с `LIMIT 1`
(на PK это no-op) не даёт втянуть его в соединение и фиксирует вложенный цикл
с точечными обращениями по PK.

Следующий шаг, если доля товаров без остатка станет большой: флаг
`products.in_stock`, который меняется только при переходе `available` через 0
(редко), и индекс `(type, sku) WHERE active AND in_stock` — тогда фильтр по
остатку уходит в индекс товаров, а `product_stock` читается только ради числа.

## 7. Что сознательно упрощено

- Нет аутентификации на `/admin/*` и заглушках — задание не просит, а
  воспроизводимость через `curl` важнее.
- Одна валюта; суммы в целых рублях, как в каталоге. Возвратов нет — `paid`
  после `payment_failed` только попадает в сверку.
- Схема через `synchronize`, миграций нет.
- Поставщики-заглушки в том же процессе и той же базе — но вызываются по HTTP с
  настоящими таймаутами; их состояние (`supplier_keys`) — «чужие» данные,
  приложение к ним не обращается.
- Тесты очищают сконфигурированную базу.

## 8. Как масштабировать под нагрузку

- **Горизонтально — уже сейчас.** Экземпляры делят только Postgres; воркеры
  разбирают очередь через `SKIP LOCKED`, восстановление идемпотентно, тесты это
  моделируют двумя приложениями на одной базе.
- **Путь вебхука** — две-три короткие команды под блокировкой одной строки;
  конкуренция возможна только между событиями *одного* заказа, что и требуется.
  Пул соединений — единственный ресурс, за которым надо следить: ожидающие
  блокировку транзакции держат соединение, поэтому HTTP к поставщику вынесен
  из транзакции.
- **Очередь.** Частичный индекс `orders (status, updated_at) WHERE status IN
  ('paid','delivering',…)` вместо полного, чтобы горячая часть не росла с историей;
  архивирование финальных заказов старше N дней в отдельную таблицу/партицию.
  При росте за пределы одного Postgres — та же таблица как outbox в брокер.
- **Поставщики.** Per-supplier circuit breaker (после K определённых отказов
  подряд идти сразу к B), лимит одновременных запросов на поставщика, джиттер в
  бэкоффе. Политика по таймауту не меняется: она про корректность, а не про
  скорость.
- **Витрина.** Запрос уже O(страницы); дальше — read-replica для чтения
  каталога и кэш страниц с инвалидацией по `product_stock.updated_at`;
  счётчик остатка обновляется в транзакции выдачи, поэтому расхождений с базой
  у кэша нет — только запаздывание.
- **Наблюдаемость.** Логи уже структурированные; следующий шаг — метрики по
  `delivery_attempts` (латентность и доля исходов по поставщику) и алерт на
  `paidNotDelivered` старше порога из сверки.
